Aspartame 개발 가이드

Windows 11용 경량 이미지 뷰어를 Rust로 만든 과정, 소스 구조, 동작 원리, 빌드와 배포 방법
Rust 1.98 eframe / egui 0.36.2 image 0.25.10 버전 0.2.0 2026-09-13

1.소개

Aspartame는 Windows 11에서 쓰기 위해 직접 만든 이미지 뷰어입니다. 설치 프로그램 없이 aspartame.exe 하나로 실행되며, 외부 DLL에 의존하지 않습니다.

  • 지원 포맷: PNG, JPEG, BMP, GIF(첫 프레임), WebP, TIFF, ICO, TGA, CR3(캐논 RAW, 파일에 내장된 JPEG로 표시, HDR PQ 촬영 파일 제외)
  • 핵심 기능 1: 창 크기에 꽉 차게 보기. 창 크기를 바꾸면 자동으로 다시 맞춥니다.
  • 핵심 기능 2: 좌우 방향키로 같은 폴더의 이미지를 이름순으로 이동합니다. Windows 탐색기와 같은 자연 정렬이라 img2가 img10보다 앞에 옵니다.
  • 실제 크기(모니터 픽셀 1:1), 커서 기준 확대/축소, 드래그 이동, 전체 화면, 드래그 앤 드롭, 명령줄 인자 열기
  • 백그라운드 디코딩과 앞뒤 이미지 미리 읽기, EXIF 회전 자동 적용, GPU 한계를 넘는 초대형 이미지 자동 축소
이 문서는 배포 zip에 함께 들어 있는 사용자 겸 개발자 가이드입니다. 소스 코드는 C:\workspace\aspartame에 있으며, 개발 계획서(DEVELOPMENT_PLAN.md / .html)와 짝을 이룹니다.

2.사용 가이드

2.1 실행과 등록

파일역할
aspartame.exe뷰어 본체. 더블클릭해 열거나, 이미지를 이 파일 위로 끌어다 놓거나, aspartame.exe 사진.jpg처럼 인자로 실행합니다.
register-default-viewer.batWindows 기본 이미지 뷰어 후보로 등록합니다. 관리자 권한이 필요 없습니다. 자세한 동작은 7장.
unregister-default-viewer.bat등록을 되돌립니다. /purge를 붙이면 복사해 둔 exe도 지웁니다.
사용법.txt, README.md짧은 안내문과 개발자용 README.
개발가이드.html이 문서.
  1. register-default-viewer.bat를 실행합니다. exe가 %LOCALAPPDATA%\Programs\Aspartame로 복사되고 레지스트리에 등록됩니다.
  2. 자동으로 열리는 설정 > 앱 > 기본 앱 > Aspartame 페이지에서 [기본값으로 설정] 단추를 누르거나, 확장자를 하나씩 눌러 Aspartame를 고릅니다.
  3. 이후 탐색기에서 이미지를 더블클릭하면 Aspartame로 열립니다.
Windows 10/11은 보안상 스크립트가 기본 앱을 직접 바꾸는 것을 막습니다. 그래서 2번 단계의 마지막 선택만은 사용자가 설정 창에서 직접 해야 합니다. 대신 스크립트가 필요한 등록을 모두 해 두고 해당 페이지를 바로 열어 줍니다.

2.3 문제 해결

증상원인과 대응
exe가 "애플리케이션 제어 정책" 메시지와 함께 실행되지 않음Windows 11 Smart App Control이 서명 없는 실행 파일을 차단합니다. Windows 보안 > 앱 및 브라우저 컨트롤 > Smart App Control 설정에서 끕니다. 한 번 끄면 Windows 재설치 전까지 다시 켤 수 없습니다.
메뉴와 안내 문구가 영어로 나옴C:\Windows\Fonts\malgun.ttf(맑은 고딕)를 찾지 못한 경우입니다. egui 기본 폰트에는 한글 글꼴이 없어, 시스템 폰트가 없으면 영어 문구로 대체합니다. 창 제목과 파일명은 OS가 그리므로 항상 한글로 보입니다.
매우 큰 이미지가 실제 크기(100%)에서도 약간 흐림GPU 텍스처 한계(보통 8192 또는 16384px)를 넘는 이미지는 표시용으로 축소해 올립니다. I 정보 오버레이에 "표시용 축소" 줄이 나타납니다.
손상 파일을 열면 빨간 오류 문구가 뜸정상 동작입니다. 창 제목에 "파일명 — 오류"가 표시되고, 방향키로 다음 파일로 넘어갈 수 있습니다.
파일을 지운 뒤 방향키가 이상함이동 대상이 사라지면 자동으로 폴더를 다시 읽고 가장 가까운 파일로 갑니다. 새로 추가된 파일은 F5로 반영합니다.

5.동작 원리

5.1 프레임 흐름

eframe 0.36은 매 프레임 App::logic()을 먼저, 그다음 App::ui()를 호출합니다. Aspartame는 두 메서드를 다음처럼 나눠 씁니다.

입력 원천명령줄 인자
드래그 앤 드롭
Ctrl+O 대화상자
방향키 / 휠 / 메뉴
→
Navigator폴더 스캔
이름순 정렬
현재 인덱스 관리
→
ImageLoader (스레드)디코딩 → RGBA8
EXIF 회전
초대형 축소
→
ViewerApp::logic결과 수신
GPU 텍스처 업로드
캐시 갱신, 프리로드 요청
→
ViewerApp::uiViewport 계산
이미지·오버레이 그리기

  1. logic: 백엔드가 알려 주는 GPU 최대 텍스처 크기(max_texture_side)를 읽고, 첫 프레임이면 명령줄 인자 파일을 연 뒤, 로더 스레드가 보낸 결과를 모두 꺼내 처리합니다.
  2. ui: 이번 프레임의 입력을 Action 목록으로 바꾸고, 캔버스 영역에서 드래그·더블클릭·우클릭 메뉴를 처리한 뒤 액션을 적용하고, 이미지와 오버레이를 그립니다. 마지막에 창 제목과 커서 상태를 갱신합니다.

5.2 백그라운드 디코딩

image_loader.rs는 스레드 하나와 채널 두 개(요청, 결과)로 이루어집니다. UI 스레드는 절대 디코딩을 하지 않으므로 큰 사진을 열어도 창이 멈추지 않습니다.

요청 구조

LoadRequest { path, generation, priority: Primary | Preload, max_side }
LoadResult  { path, generation, priority, result: Ok(DecodedImage) | Err(String) }
  • generation: 사용자가 이동할 때마다 1씩 증가하는 번호입니다. 결과가 돌아왔을 때 번호가 현재와 다르면 이미 지나간 요청이므로 캐시에만 넣고 화면은 바꾸지 않습니다.
  • 마지막 요청 우선: 방향키를 연타하면 요청이 쌓입니다. 워커는 디코딩 하나를 시작하기 전에 큐를 전부 비워 가장 새로운 Primary만 남기고, 그보다 오래된 Primary와 프리로드는 버립니다. 열 장을 빠르게 넘겨도 중간 이미지를 헛되이 디코딩하지 않습니다.
  • 프리로드: 이미지가 화면에 뜨면 이름순으로 앞뒤 한 장씩 Preload로 요청합니다. 다음 방향키를 누르면 대부분 캐시에서 즉시 나옵니다.
  • 중복 제거: 같은 파일이 프리로드와 Primary로 겹쳐 있으면 한 번만 디코딩합니다.
  • 결과를 보낸 뒤 ctx.request_repaint()로 UI 스레드를 깨웁니다.

decode() 단계

  1. 파일 크기를 읽고(정보 오버레이용) ImageReader::open으로 엽니다. 기본 메모리 제한이 정상적인 대형 사진도 거부하므로 no_limits()를 호출합니다.
  2. with_guessed_format()으로 확장자가 아닌 내용으로 포맷을 판별합니다. 확장자가 틀린 파일도 열립니다.
  3. into_decoder() → orientation()으로 EXIF 방향을 읽고, 디코딩 후 apply_orientation()으로 회전·반전을 적용합니다. 스마트폰 세로 사진이 올바른 방향으로 나옵니다.
  4. 긴 변이 max_side(GPU 한계)를 넘으면 비율을 유지한 채 FilterType::Triangle로 축소합니다. 원본 크기는 별도로 보관해 제목과 정보에 표시합니다.
  5. into_rgba8()로 스트레이트 알파 RGBA8 버퍼를 만들어 UI 스레드로 넘깁니다.

CR3는 cr3.rs가 먼저 처리합니다. 파일 앞부분의 ftyp 브랜드로 판별한 뒤 RAW를 현상하지 않고 카메라가 넣어 둔 가장 큰 JPEG를 꺼내 위 단계로 넘깁니다. 내장 JPEG에는 EXIF가 없어 회전 정보는 컨테이너의 CMT1 상자에서 읽습니다. HDR PQ로 촬영한 파일은 미리보기가 모두 HEVC라서 오류 메시지를 표시합니다.

5.3 이름순 폴더 탐색

navigator.rs는 열린 파일의 폴더를 한 번 스캔해 지원 확장자만 남기고 정렬한 목록과 현재 인덱스를 들고 있습니다.

자연 정렬 알고리즘 (natural_cmp)

두 파일명을 앞에서부터 한 글자씩 비교하되, 양쪽 모두 숫자가 시작되면 숫자 덩어리를 통째로 잘라 값으로 비교합니다.

  1. 둘 다 숫자면: 앞의 0을 뗀 뒤 길이(자릿수)를 먼저, 같으면 문자열을 비교합니다. 값이 같으면 0이 적은 쪽(1 < 01)이 앞섭니다.
  2. 그 외에는 두 문자를 소문자로 바꿔 비교합니다. 대소문자를 무시하므로 a.png와 B.png가 알파벳순으로 섞입니다.
  3. 끝까지 같으면 원래 문자열의 바이트 비교로 순서를 고정해 결과가 항상 결정적입니다.
입력:  photo10.jpg, Photo2.jpg, photo1.jpg, 가.png, readme.txt, b.PNG
결과:  b.PNG, photo1.jpg, Photo2.jpg, photo10.jpg, 가.png    (readme.txt 제외)

한글은 유니코드 코드포인트 순이라 가나다순이 되고, 라틴 문자 뒤에 옵니다. Windows 탐색기의 기본 "이름" 정렬과 같은 결과를 목표로 했습니다.

이동 규칙

  • step(±1)은 끝에서 순환합니다(wrap = true). 이미지가 한 장이면 아무 동작도 하지 않습니다.
  • peek(±1)은 이동하지 않고 이웃 경로만 돌려주며, 프리로드와 캐시 보존 대상을 정할 때 씁니다.
  • 지원하지 않는 확장자(readme.txt 등)를 직접 열면 목록의 정렬 위치에 끼워 넣어 그 파일에서도 앞뒤로 이동할 수 있게 합니다.
  • refresh()는 폴더를 다시 읽고, 현재 파일이 사라졌으면 그 자리를 차지한 파일(정렬상 다음 파일)을 선택합니다. 로더가 "파일 없음" 오류를 돌려주면 자동으로 호출됩니다.
  • 같은 폴더 안에서는 대소문자만 다른 이름을 같은 파일로 봅니다(Windows 파일 시스템 특성).

5.4 창에 맞춤과 확대

viewport.rs는 화면에 그릴 사각형을 결정하는 순수 계산 모듈입니다. 상태는 세 가지입니다.

enum ZoomMode { Fit, Actual, Custom }
struct Viewport { mode, scale /* 논리 포인트 / 이미지 픽셀 */, pan /* 이미지 중심의 창 중심 대비 오프셋 */ }

창에 꽉 차게 (Fit)

scale  = min(W / w, H / h)        // 창 W×H, 이미지 w×h
draw   = 창 중심에 (w·scale) × (h·scale) 크기로 배치

매 프레임 layout()이 다시 계산하므로 창 크기를 바꾸거나 전체 화면으로 전환하면 즉시 따라갑니다. 창보다 작은 이미지도 확대해서 채웁니다. 이미지가 바뀔 때마다 이 모드로 초기화됩니다.

실제 크기 (Actual)

"100%"는 물리 픽셀 기준입니다. egui는 논리 포인트 단위로 그리므로 scale = 1 / pixels_per_point로 두어야 이미지 1픽셀이 모니터 1픽셀에 대응합니다. 150% 배율 모니터에서도 흐려지지 않습니다. 제목의 배율 표시는 scale × pixels_per_point × 100입니다.

커서 기준 확대 (Custom)

// 커서 m, 현재 이미지 중심 c, 배율 s0 → s1
c' = m − (m − c) · (s1 / s0)      // 커서 아래 이미지 지점이 그대로 머무는 새 중심

휠 한 칸에 1.25배, 범위는 물리 픽셀 기준 1%~3200%입니다. 키보드 +/-는 창 중심을 기준점으로 씁니다.

이동 범위 제한 (clamp_pan)

그려진 이미지가 창보다 작은 축은 오프셋을 0으로 고정해 가운데 정렬하고, 큰 축은 이미지 가장자리가 창 안쪽으로 들어와 빈틈이 생기지 않는 범위로 제한합니다.

5.5 텍스처 캐시

디코딩된 이미지는 ColorImage::from_rgba_unmultiplied로 변환해 ctx.load_texture로 GPU에 올립니다. 필터는 확대·축소 모두 Linear이고 밉맵을 켜서, 사진을 15%처럼 크게 축소해 볼 때 생기는 반짝임(앨리어싱)을 줄입니다.

  • TextureCache는 경로를 키로 하는 LRU 목록입니다. 최대 3장, 총 512MB 예산을 넘으면 오래된 것부터 지웁니다.
  • 지우지 않는 것: 지금 보이는 이미지, 이동 목표, 이름순 앞뒤 한 장. 앞뒤로 오갈 때 다시 디코딩하지 않습니다.
  • 이동 목표가 캐시에 있으면 로더를 거치지 않고 즉시 전환합니다.

5.6 입력 처리

input.rs의 collect_actions()는 egui의 InputState를 읽어 프레임마다 Action 목록을 만듭니다. 앱 로직은 키 코드가 아니라 액션만 보므로 단축키를 바꾸기 쉽습니다.

  • 키: 방향키/PageUp/PageDown → Next/Prev, Home/End, F/0 → Fit, 1 → ActualSize, +/=/- → 확대·축소, F11, Esc, F5, I, Ctrl+O.
  • 휠: Event::MouseWheel을 단위별로 "칸" 수로 환산합니다(Line은 1칸, Point는 50포인트당 1칸, Page는 5칸). 한 프레임의 칸 수를 합쳐 ZoomBy(1.25^칸) 하나로 보냅니다.
  • 드롭: raw.dropped_files의 경로를 모아 OpenPaths로 보내고, 첫 번째 실제 파일을 엽니다.
  • 마우스 드래그, 더블클릭, 우클릭 메뉴는 캔버스의 Response에서 처리합니다. 메뉴가 열린 프레임의 Esc는 종료로 이어지지 않도록 Popup::is_any_open으로 걸러 냅니다.
  • egui 기본 동작인 Ctrl++/- UI 배율 변경은 이미지 확대와 충돌하므로 zoom_with_keyboard = false로 끕니다.

5.7 그리기와 창 제어

  • 캔버스: CentralPanel에 여백 없는 프레임을 씌우고 전체 영역을 Sense::click_and_drag로 인터랙션 대상으로 잡습니다. 이미지는 painter.image(texture, rect, uv, WHITE) 한 줄로 그립니다.
  • 오버레이: 정보 패널(I)은 줄마다 갤리를 만들어 최대 너비로 반투명 상자를 그린 뒤 배치합니다. 오류는 파일명(흰색)과 원인(빨간색)을 가운데에, 로딩 스피너는 150ms 이상 걸릴 때만 우하단에, 드롭 힌트는 파일을 창 위로 끌고 올 때 테두리와 함께 표시합니다.
  • 한글 폰트: 시작 시 %SystemRoot%\Fonts\malgun.ttf를 읽어 egui 폰트 패밀리 끝에 추가합니다. 라틴 글자는 egui 기본 폰트, 한글은 맑은 고딕으로 대체됩니다. 폰트가 없으면 UI 문구를 영어로 바꿉니다.
  • 창 제목: 값이 바뀔 때만 ViewportCommand::Title을 보냅니다. 전체 화면은 ViewportCommand::Fullscreen, 종료는 Close, 커서 숨김은 CursorVisible입니다.
  • 배경: clear_color와 패널 채우기를 같은 진회색(#1C1C1E)으로 맞춰 창 크기 변경 중에도 깜빡이지 않습니다.

7.기본 앱 등록 스크립트

register-default-viewer.bat는 관리자 권한 없이 현재 사용자 레지스트리(HKCU)에만 기록합니다. 단계별 동작은 다음과 같습니다.

  1. exe 찾기: 인자로 준 경로 → 스크립트 옆의 aspartame.exe → ..\target\release\aspartame.exe 순서로 찾습니다.
  2. 복사: %LOCALAPPDATA%\Programs\Aspartame\aspartame.exe로 복사합니다. 빌드 폴더를 지워도 연결이 깨지지 않게 하기 위해서입니다.
  3. 파일 형식 등록 (HKCU\Software\Classes\Aspartame.Image): 표시 이름, DefaultIcon, shell\open\command = "exe" "%1"
  4. 기본 프로그램 등록 (HKCU\Software\Aspartame\Capabilities + HKCU\Software\RegisteredApplications): 앱 이름·설명·아이콘과 FileAssociations에 13개 확장자 → Aspartame.Image. 이 등록 덕분에 설정 > 기본 앱 목록과 "연결 프로그램" 목록에 나타납니다.
  5. 연결 후보 추가: 각 확장자의 OpenWithProgids에 Aspartame.Image를 추가합니다. 기존 기본 앱은 건드리지 않습니다.
  6. 셸 알림: PowerShell로 SHChangeNotify(SHCNE_ASSOCCHANGED)를 호출해 탐색기가 캐시를 갱신하게 합니다.
  7. 설정 열기: ms-settings:defaultapps?registeredAppUser=Aspartame로 Aspartame 페이지를 엽니다. 여기서 사용자가 확장자를 고르면 끝입니다.

unregister-default-viewer.bat는 위 키와 값을 모두 삭제하고, /purge를 주면 복사한 exe 폴더도 지웁니다. Aspartame가 기본 앱이던 확장자는 다음에 열 때 Windows가 사용할 앱을 다시 묻습니다.

bat 파일은 UTF-8(BOM 없음) + CRLF로 저장되어 있고 첫 줄에서 chcp 65001을 실행합니다. LF 줄 끝으로 저장하면 for (...) 블록이 깨지므로 편집기에서 CRLF를 유지하세요.

9.개발 과정과 결정

1) 계획

요구사항(대중적 포맷, 창에 꽉 차게 보기, 좌우 방향키 이름순 이동)을 정리하고 GUI 프레임워크를 비교해 egui를 골랐습니다. Phase 0~5(환경, 한 장 표시, 줌/팬, 폴더 탐색, 백그라운드 로딩, 전체 화면)로 나눈 계획서를 md와 html로 작성했습니다.

2) 최신 API 조사

착수 시점의 최신 버전(eframe 0.36.2)은 계획 당시 알던 API와 달랐습니다. App::update가 App::ui(&mut Ui, &mut Frame)와 App::logic(&Context, &mut Frame)으로 나뉘었고, CentralPanel::show가 &Context 대신 &mut Ui를 받으며, 드롭 파일이 Arc<dyn DroppedFile> 핸들로 바뀌었습니다. docs.rs와 GitHub 태그 소스를 대조해 시그니처를 확인한 뒤 코드를 작성했습니다.

3) Smart App Control 차단

코드를 다 쓴 뒤 컴파일하려 하자 Windows 11 Smart App Control이 서명 없는 cargo.exe를 차단했습니다(os error 4551). 이 PC에는 WSL, Docker, git도 없어 우회 빌드도 불가능했고, 정책 해제는 되돌릴 수 없는 시스템 변경이라 사용자 판단에 맡겼습니다. 그동안 등록 bat, 패키징 스크립트, 배포 폴더를 먼저 만들어 검증했습니다.

4) 빌드와 검증

정책 해제 후 첫 릴리스 빌드가 한 번에 성공했고(경고 1개는 정리), 단위 테스트 14개가 통과했습니다. 실행 검증에서 두 가지를 고쳤습니다. 손상 파일을 열었을 때 제목에 파일명이 빠지던 것, 그리고 컨텍스트 메뉴를 Esc로 닫으면 앱까지 종료되던 것입니다.

설계상 주요 선택

  • 이미지 전환 시 항상 창에 맞춤으로 초기화: 방향키만으로 넘겨 보는 사용 방식에 가장 자연스럽습니다.
  • "100%"를 물리 픽셀로 정의: HiDPI 모니터에서 실제 크기가 흐려지지 않게 하려는 요구사항 때문입니다.
  • ProgID + Capabilities 등록: assoc/ftype은 관리자 권한이 필요하고 Windows 10/11의 사용자 선택(UserChoice)에 밀립니다. 정식 등록 후 설정 페이지를 열어 주는 방식이 정책을 우회하지 않으면서 가장 짧은 경로입니다.
  • exe를 LOCALAPPDATA로 복사해 등록: 빌드 폴더 정리나 이동으로 연결이 깨지는 일을 막습니다.
  • 밉맵 켜기: 큰 사진을 작게 볼 때의 화질이 뷰어의 첫인상을 좌우합니다.
